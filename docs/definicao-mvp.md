# Definição do MVP — Acompanha BusUCSal

> Documento estruturado conforme o **Anexo C** e as diretrizes técnicas **POOALAB (Versão 1.1 — Semestre 2026.2)** da UCSal.

---

##  Anexo C — Definição Oficial do MVP

| Campo Oficial (Anexo C) | Definição no Projeto Acompanha BusUCSal |
| :--- | :--- |
| **Solução** | **Acompanha BusUCSal** — Plataforma web responsiva (API REST Spring Boot + SPA React/Leaflet) para acompanhamento do ônibus universitário Expresso UCSal no Campus Pituaçu. |
| **Usuário principal** | Estudantes (com suporte visual também para professores e funcionários) da UCSal Pituaçu que precisam embarcar nos pontos da Av. Paralela / Av. Pinto de Aguiar ou acompanhar a saída do ônibus. *(Perfis secundários na API: `MOTORISTA` para iniciar viagem/enviar GPS/registrar incidentes e `ADMIN` para gerenciar cadastros.)* |
| **Resultado principal** | O usuário visualiza, em uma única tela com mapa interativo e painel de status, onde o ônibus está no trajeto, a distância restante até o campus, o tempo estimado de chegada (ETA em minutos) e a próxima saída programada na grade horária oficial. |
| **Fluxo de ponta a ponta** | **Entrada:** Usuário informa matrícula fictícia e perfil (`Aluno`, `Professor` ou `Funcionário`) na tela `Login.jsx` (ou autentica via e-mail/senha na API `POST /v1/auth/login` como `ADMIN`/`MOTORISTA`/`ALUNO`).<br>**Processamento:** O adaptador `frontend/src/services/api.js` carrega a rota ativa (`GET /v1/rota`), as paradas ordenadas (`GET /v1/ponto-parada/{idRota}`), a viagem ativa (`GET /v1/viagem`) e a última posição GPS (`GET /v1/posicaoGPS/ultima/{idViagem}`), ou executa o simulador determinístico `mock.js` (quando `VITE_USE_MOCK=true`), calculando distância restante via fórmula de Haversine, velocidade útil e ETA em minutos; em paralelo, `utils/horarios.js` calcula a próxima saída do dia.<br>**Resultado:** O componente `Mapa.jsx` renderiza o trajeto, os pontos de parada e o marcador do ônibus atualizado a cada 3 segundos; o painel de `Home.jsx` exibe status textual (`Procurando o ônibus...`, `A caminho do campus`, `Chegando ao campus`), ETA, km restantes e botão para o modal `Horarios.jsx`. |
| **Critérios de pronto** | 1. **Código:** API backend compilando com migrações Flyway `V1`–`V3` aplicadas no PostgreSQL; frontend compilando com `npm run build` e executando sem erros de console no fluxo principal.<br>2. **Testes:** Casos do caminho principal, erros previsíveis (matrícula inválida, credenciais inválidas, rota/viagem inexistente, erro HTTP 400/401/404/409) e teste em ambiente limpo documentados e validados conforme [`tests/ROTEIRO_TESTES.md`](../tests/ROTEIRO_TESTES.md).<br>3. **Documentação:** `README.md`, `docs/*`, `demo/ROTEIRO_DEMO.md`, `tests/ROTEIRO_TESTES.md` completos, com `docs/declaracao-ia-terceiros.md` assinada e `docs/pitch.pdf` exportado.<br>4. **Integração e Demo:** Código da branch `simulacao` mesclado para `main`; demonstração executável ao vivo com dados sintéticos pré-carregados e plano de contingência testado. |
| **Maior risco e mitigação** | **Risco principal (Técnico / Integração):** Divergência de contrato entre o login do frontend (`{ matricula, perfil }` + `VITE_MOCK_LOGIN=true` gerando `'token-mock'`) e a segurança JWT do backend (`POST /v1/auth/login` exigindo `{ email, senha }` e bloqueando `GET /v1/**` com HTTP 401 sem token JWT válido), somada à dependência de banco PostgreSQL local no dia da mostra.<br>**Mitigação:** (1) Alinhar o endpoint/fluxo de login ou política de acesso antes do congelamento; (2) Manter o **Modo Simulado (`VITE_USE_MOCK=true`)** pronto como contingência local instantânea para a demonstração visual da jornada do aluno, combinado à demonstração direta da API autenticada via Swagger UI (`/swagger-ui/index.html`) e dados seed pré-carregados. |
| **Teste principal** | Seguir o roteiro de ponta a ponta descrito em [`tests/ROTEIRO_TESTES.md`](../tests/ROTEIRO_TESTES.md) em ambiente limpo (máquina diferente da de desenvolvimento) usando apenas o `README.md`, verificando carregamento de rota, paradas, movimentação do marcador do veículo, atualização de ETA/distância e exibição da próxima saída sem erros inesperados. |
| **Limitações conhecidas** | 1. Sem hardware GPS real embarcado na frota (posições dependem de envio via API `POST /v1/posicaoGPS` ou simulação cíclica de 3 minutos em `mock.js`).<br>2. Sem integração institucional com o sistema acadêmico da UCSal.<br>3. Contrato de login frontend (`matricula`/`perfil`) ainda divergente do backend (`email`/`senha`), exigindo ajuste ou uso separado de mock visual + Swagger para testes integrados.<br>4. Operações do motorista (`ViagemController`, `PosicaoGpsController`, `IncidenteController`) e do admin (`UsuarioController`, `VeiculoController`, `RotaController`, `PontoParadaController`) existem apenas na API REST/Swagger, sem telas dedicadas no frontend.<br>5. Apenas `BuscsalApplicationTests.contextLoads()` existe como teste automatizado no backend, e `origin/main` aguarda merge da branch `simulacao`. |
